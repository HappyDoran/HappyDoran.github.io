이미지 업로드 기능을 WebView와 네이티브에 나눠 구현할 때는 파일의 소유자와 요청 순서를 결정하는 주체가 달라진다\. 네이티브는 파일과 플랫폼 기능을 관리하고, Web은 입력·업로드 세션·분석 요청을 조율하도록 책임을 나누는 방법을 살펴본다\.

이 글은 구성 요소의 책임과 이미지 수명에 집중한다\. 필드별 규칙은 keypoint API 계약, polling과 화면 경합은 비동기 분석 흐름 문서에서 다룬다\. 아래 크기·시간 값은 설계 예시다\.

### 이미지 준비와 로컬 파일 수명

1. 카메라 또는 앨범에서 이미지를 확보하고 keypoint를 검출한다\.
1. 이미지 방향을 up으로 반영하고 JPEG로 정규화한다\. 긴 변 최대 2048px 같은 크기 정책은 서버 계약과 함께 정한다\.
1. 고정 순서의 N개 keypoint를 만든다\. 검출하지 못한 점은 초기화 상태로 표시한다\.
1. 리뷰에서 확인·조정하며 미확인 점이 남으면 완료를 막는다\.
1. 최종 바이트의 SHA\-256, 크기, 해상도를 계산한다\.
1. captureId를 발급하고 임시 파일 registry에 등록한다\.
1. 조회 키·메타데이터·미리보기·keypoint만 Web에 반환한다\.

네이티브 로컬 경로는 결과 계약에 노출하지 않는다\. 브라우저도 같은 캡처 결과를 만들되 이미지는 페이지 메모리에 보관할 수 있다\. 이 경우 새로고침에 따른 유실을 고려해야 한다\.

### 브리지와 요청 상관관계

```text
촬영 요청
  → Native open()
  → 촬영 완료 또는 취소

이미지 업로드 요청
  → Native uploadCapture(captureId, url, method, headers)
  → 업로드 완료 또는 실패
```

Web과 Native는 같은 Zod schema로 요청·결과를 검증한다\. 업로드 완료 응답의 captureId와 uploadId가 대기 중인 요청과 모두 일치할 때만 Promise를 완료한다\. 다른 요청의 늦은 응답으로 작업이 완료되지 않게 하는 장치다\.

네이티브 registry 조회와 PUT 직전에는 로컬 파일 존재 여부도 확인한다\.

### Web 오케스트레이션

```text
IDLE → CAPTURE_READY → REQUESTING_UPLOAD_URL
     → UPLOADING_IMAGE → SUBMITTING_ANALYSIS
     → POLLING_ANALYSIS
오류 → FAILED
```

Zustand는 클라이언트 준비 작업을, TanStack Query는 서버의 running·succeeded·failed 상태를 소유한다\.

준비 함수는 업로드 세션 생성 → 바이너리 PUT → 분석 생성 → 로컬 캡처 해제를 순서대로 실행한다\. upload·release adapter가 네이티브와 브라우저 차이를 처리하면 호출부가 플랫폼을 분기하지 않아도 된다\.

예시로 단건 query는 running을 처음 관측한 시점부터 3분 동안 2초 간격으로 조회한다\. 완료 시 navigation lock이 해제된 뒤 결과 화면으로 replace한다\.

개발용 예시 응답은 테스트 fixture로 분리한다\. 실행 경로에서는 실제 작업 상태와 결과 계약을 확인하며, 오류를 예시 결과로 덮지 않는다\.

### 해제와 정리 정책

분석 생성 성공 후 로컬 이미지를 해제한다\. 새 이미지 준비와 처음부터 다시 시작에서도 이전 이미지를 정리한다\. 브라우저에서는 같은 adapter가 메모리 이미지를 제거한다\.

registry는 오래된 기록을 정리할 수 있어야 한다\. 예를 들어 다음 등록 시 24시간이 지난 기록을 지우는 정책을 사용할 수 있지만, 즉시 주기 정리와 같은 의미로 해석하지 않는다\.

로컬 파일 해제와 저장소 객체 삭제는 서로 다른 작업이다\. 실패·취소 객체 보존, 서명 URL 만료 후 재발급은 별도 계약으로 정해야 한다\.

분석 제출의 성공 여부가 불명확하면 준비 POST 전체를 자동 반복하지 않는다\. 새 세션으로 제출하면 분석이 중복 생성될 수 있다\.

전체 재시도와 조회 재시도를 분리한다\. 처리 중 화면은 시작 여부 ref로 초기 중복 실행을 막고, navigation lock으로 전환 중 중복 화면 이동을 제어한다\. 화면을 떠난 뒤 도착한 결과는 store에 반영하거나 화면 이동에 사용하지 않는다\.

### 전송·보안·검증

- 발급된 URL과 headers는 그대로 사용하며 클라이언트에서 host를 바꾸지 않는다\.
- 원본 바이너리·로컬 경로를 분석 JSON에 넣지 않고 직접 PUT한다\.
- preview data URL은 화면 표시용이다\.
- 브라우저 PUT의 CORS와 HTTPS·[localhost](<http://localhost/>) checksum 생성을 확인한다\.
- 토큰은 BFF HttpOnly cookie로 관리하고 이미지·입력값·서명 URL·토큰을 로그에 남기지 않는다\.

공통 schema, builder, 식별자 상관관계, 요청 순서, polling, 실패 문구, 화면 경합은 자동 테스트 대상으로 나눌 수 있다\. 네이티브 권한·촬영·실제 PUT, 저장소 CORS·만료와 객체 정리 정책은 별도로 확인한다\. 클라이언트 테스트 통과를 서버의 객체 검증·보존 정책 구현 증거로 삼지 않는다\.

### 정리

- 파일은 네이티브·브라우저가 보관하고 Web이 요청 순서를 조율한다\.
- 세 종류의 ID를 수명과 신뢰 범위에 맞게 구분한다\.
- 응답 상관관계·중복 실행·화면 이탈을 각각 다룬다\.
- 로컬 이미지 해제와 서버 객체 정리를 별도 정책으로 관리한다\.

iOS 앱의 토큰 기반 인증은 로그인 성공 이후의 저장·복원·만료 처리까지 이어져야 한다\. Access Token과 Refresh Token을 구분하고 앱 진입과 사용 중 갱신을 일관된 흐름으로 구성하는 방법을 정리한다\.

### 목표와 제약

인증 코드는 흐름을 추적할 수 있어야 하며 토큰의 안전한 저장, 명확한 오류 처리, 동시성 제어를 함께 고려해야 한다\. 이 글은 Keychain을 저장 경계로 사용하는 흐름을 전제로 하며 Keychain wrapper의 구체 구현은 다루지 않는다\.

### 두 토큰의 역할

일반적으로 Access Token은 더 짧은 유효기간을, Refresh Token은 더 긴 유효기간을 갖도록 구성한다\. 실제 수명과 회전 방식은 서버 계약에 따른다\.

평소에는 Access Token으로 요청하고 갱신이 필요할 때 Refresh Token을 사용한다\. 토큰 갱신과 새 사용자 로그인은 서로 다른 경로다\.

### 최초 로그인

1. 사용자가 Sign in with Apple을 실행한다\.
1. provider가 반환한 인증 결과를 서버 계약에 맞춰 전달한다\.
1. 서버의 로그인 응답에서 Access Token과 Refresh Token을 받는다\.
1. 두 토큰을 정해진 로컬 저장 경계에 보관한다\.
1. 클라이언트가 만료 시각을 추적하는 경우 사전 갱신 판단에 사용한다\.

클라이언트의 만료 시각 추적을 서버의 토큰 유효성 판정을 대신하는 것으로 해석하지 않는다\. provider 결과의 필드도 항상 동일하게 존재한다고 가정하지 않고 서버의 요청 계약에 맞춰 사용한다\.

### 앱 진입 시 세션 복원

1. 저장된 Refresh Token을 조회한다\.
1. 값이 있으면 갱신 API로 세션 복원을 시도한다\.
1. 응답의 새 Access Token을 저장하고, Refresh Token도 갱신됐다면 함께 반영한다\.
1. 사용자 정보를 갱신하고 인증된 화면으로 진입한다\.
1. 토큰이 없거나 더 이상 사용할 수 없다면 로그인 경로로 이동한다\.

앱 진입 시 refresh를 실행하는 것은 세션 복원 정책의 한 선택이다\. 모든 앱에 무조건 가장 좋은 갱신 시점이라고 단정하지 않고 서버의 수명·회전 계약과 맞춰야 한다\.

### 앱 사용 중 Access Token 갱신

인증 요청에는 저장된 Access Token을 헤더로 전달한다\. 클라이언트가 추적하는 만료 시각과 요청 결과를 통해 갱신이 필요한 상황을 구분한다\.

갱신이 필요하면 Refresh Token을 조회해 서버에 보내고, 응답의 새 토큰을 저장한 뒤 이후 요청에 사용한다\. Refresh Token을 사용할 수 없다면 다시 로그인해야 한다\.

여러 요청이 같은 시점에 만료를 만날 수 있으므로 동시성 제어를 설계 범위에 포함한다\. 이 글의 흐름 설명만으로 동시 갱신이 해결됐다고 보지는 않는다\.

### 오류와 저장 경계

- 최초 로그인 실패와 저장된 세션 복원 실패를 구분한다\.
- 토큰 저장과 사용자 정보 갱신의 순서를 명시한다\.
- 갱신 응답에서 바뀐 토큰을 누락하지 않는다\.
- 만료된 Refresh Token을 계속 사용하지 않고 재로그인 경로를 제공한다\.
- 토큰 원문을 로그·URL·오류 안내에 포함하지 않는다\.

### 정리

토큰 인증은 최초 로그인, 앱 진입 복원, 사용 중 갱신, 재로그인의 네 흐름으로 나눌 수 있다\. Keychain 저장 경계와 서버 수명·회전 계약을 맞추고, 만료 판단과 오류·동시성 처리의 책임을 명확히 해야 한다\.

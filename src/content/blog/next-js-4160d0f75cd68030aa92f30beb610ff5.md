DB 없이 Next\.js 서버 하나로 외부 provider\(Notion, GitHub\)를 잇는 앱에서는 기능보다 <strong>코드가 어디서 실행되는가</strong>가 먼저 지켜야 할 경계가 된다\. provider token과 쿠키 해독 코드가 브라우저 번들로 새면 그 자체로 사고이기 때문이다\. 이 글은 Notion 문서를 칸반에서 관리해 GitHub Pages 블로그로 게시하는 앱에 적용한 구조를 예로, 실행 위치로 나눈 다섯 폴더와 그 위에 얹은 가벼운 Ports &amp; Adapters 패턴을 정리한다\.

이 글은 구조를 선택한 이유와 경계에 집중한다\. 폴더명과 파일명은 이 앱의 예시이며 Hexagonal Architecture나 Clean Architecture의 필수 규약으로 해석하지 않는다\.

### 구조를 정한 조건

- 실행 서버는 Next\.js 앱 하나다\. 별도 Worker, DB, 큐가 없다\.
- 사용자 데이터는 서버에 영속화하지 않는다\. 세션과 provider token은 암호화한 ` HttpOnly ` 쿠키에, 게시 결과는 사용자의 GitHub 저장소에 둔다\.
- 모든 mutation은 서버가 요청 시점에 Notion·GitHub 권한을 다시 확인한 뒤 실행한다\.
- 기능은 칸반, 게시, 사이트 설정, Notion 연결 정도로 적다\.

기능 수가 적고 서버·브라우저 경계가 보안 경계와 겹치는 앱이다\. 그래서 기능 중심\(` features/<기능>/ `\) 대신 실행 위치를 첫 번째 축으로 골랐다\.

### 다섯 폴더로 나누는 이유

```text
apps/web/
├─ app/          # Next 진입점: page, layout, api/**/route.ts, auth/**/route.ts
├─ components/   # 화면 컴포넌트와 화면 상태 hook
└─ lib/
   ├─ client/    # 브라우저에서 부르는 API 호출과 응답 검증
   ├─ shared/    # 서버·브라우저가 함께 쓰는 순수 코드 (I/O 없음)
   └─ server/    # 서버 전용: provider adapter, use case, 쿠키·OAuth
```

- 폴더 이름만 보고 그 코드가 브라우저 번들에 들어갈 수 있는지 판단할 수 있어야 한다\.
- 실제 파일이 있는 폴더만 만든다\. 미리 만든 빈 layer는 쓰이지 않는 추상화가 된다\.
- 기능 구분은 ` lib/server/ ` 아래 하위 폴더\(` auth `, ` notion `, ` github `, ` publish `, ` operations `\)로만 한다\.

타입 import는 컴파일 후 사라지므로 번들에 서버 코드를 끌고 오지 않는다\. 예를 들어 프리뷰 DTO\(` lib/shared/publish-preview.ts `\)는 서버의 문서 조립 타입을 ` import type `으로 참조하지만 브라우저에서도 안전하다\.

### app/

framework 진입점만 둔다\.

- ` page.tsx `, ` layout.tsx `, ` globals.css `
- ` api/**/route.ts `, ` auth/**/route.ts `

route 파일은 10줄 안팎으로 ` lib/server/ `의 함수 하나를 부르기만 한다\.

```typescript
export async function POST(request: Request): Promise<Response> {
  return publishNotionPage(request, createPublishDependencies());
}
```

Next\.js App Router는 ` app/ ` 아래 파일을 라우트로 해석한다\. 화면 컴포넌트를 ` app/ `에 같이 두면 &quot;이 파일이 라우트인가&quot;를 매번 확인해야 하므로 컴포넌트는 ` components/ `로 뺀다\.

### components/

화면 컴포넌트와 그 화면의 상태 hook\(` use-board.ts `, ` use-workspace.ts `\)을 둔다\. 컴포넌트 수가 적으면 하위 폴더 없이 평평하게 둔다\.

- provider token, 쿠키, provider 응답 원문을 다루지 않는다\.
- 서버 데이터는 ` lib/client/ `를 거쳐 받는다\.

### lib/client/

브라우저에서 앱 API를 부르는 함수와 응답 검증을 둔다\.

- 응답은 Zod로 검증한 뒤 typed value로 쓴다\. 같은 앱의 서버가 보낸 응답도 신뢰 경계를 한 번 넘은 값으로 본다\.
- 게시 후 배포 완료까지 polling하는 흐름처럼 여러 요청을 잇는 절차도 여기 둔다\.

### lib/shared/

서버와 브라우저가 함께 쓰는 순수 코드만 둔다\.

- 동시 실행 상한, 날짜 표시, outline 필터
- 저장소 파일 경로 규칙, 사이트 설정 schema, 프리뷰 DTO schema

조건은 하나다\. <strong>I/O가 없고 어느 런타임에서 실행해도 결과가 같아야 한다\.</strong> fetch, 쿠키, ` node:* ` 모듈이 필요해지면 그 코드는 shared가 아니다\.

### lib/server/

서버에서만 실행되는 코드를 기능별 하위 폴더로 둔다\.

```text
lib/server/
├─ auth/        # 세션·연결 쿠키, GitHub·Notion OAuth
├─ notion/      # 요청 · 응답 변환 · 읽기 순서 · 목록 route
├─ github/      # 저장소 확인 · commit · 배포 상태
├─ publish/     # 게시 · 내리기 · 프리뷰 · 보관 목록 · 사이트 설정 use case
└─ operations/  # provider 공통 timeout · Retry-After · allowlist 로그
```

이 폴더 안의 구조는 다음 절의 패턴을 따른다\.

### 가벼운 Ports &amp; Adapters

바깥 시스템과 핵심 로직 사이를 interface로 끊는다\. 정식 헥사고날의 DI 컨테이너, use case 클래스, repository 계층은 두지 않고 함수와 인자로 같은 효과를 낸다\.

</table>
</div>

게시 요청 하나의 흐름은 다음과 같다\.

```text
app/api/publish/route.ts                (controller)
  → publishNotionPage(request, deps)    (use case)
      → deps.notion.getPageContent()    (port → Notion adapter)
      → convert.ts                      (anti-corruption)
      → createMarkdownArtifact()        (pure core)
      → deps.github.commitArtifacts()   (port → GitHub adapter)
```

use case는 의존성을 인자로 받는다\. 운영 코드는 ` create*Dependencies() `가 실제 구현을 넣고, 테스트는 상태를 바꿀 수 있는 fake provider를 넣는다\. 그래서 &quot;프리뷰 뒤 원문이 바뀌면 게시는 최신 원문을 쓴다&quot; 같은 흐름을 실제 API 없이 통합 테스트로 증명할 수 있다\.

### package 경계

monorepo package는 외부 경계와 순수 로직을 나누는 데만 쓴다\.

```text
apps/web
  ├─ packages/auth
  ├─ packages/notion
  ├─ packages/github
  └─ packages/publisher
          └─ packages/domain
```

- package끼리 서로의 adapter를 import하지 않는다\. 조립은 ` apps/web `만 한다\.
- 실행 서버가 하나이므로 port 구현\(adapter\)은 package가 아니라 ` apps/web/lib/server/ `에 둔다\. package에는 계약과 순수 로직만 남는다\.
- Node 전용 구현은 ` @scope/auth/server `처럼 별도 진입점으로 분리한다\.

### import 경로

- 다른 폴더는 ` @/ ` alias로 import한다\(` @/lib/server/auth/session `\)\.
- 같은 폴더는 ` ./ `로 import한다\.

` ../../../../../../../../lib/... ` 같은 깊은 상대 경로는 라우트 깊이에 따라 달라져 읽기 어렵다\. alias로 바꾸면 lint 규칙도 ` @/lib/server/** ` 같은 단순한 패턴으로 쓸 수 있다\. alias는 ` tsconfig.json `의 ` paths `와 테스트 러너\(Vitest ` resolve.alias `\)에 같이 등록한다\.

### 경계를 lint로 강제

방향 규칙은 문서로만 두면 리뷰에서 놓친다\. ESLint의 ` @typescript-eslint/no-restricted-imports `로 막는다\.

```javascript
const serverOnly = {
  allowTypeImports: true,
  group: ["@/lib/server/**", "**/lib/server/**", "../server/**"],
  message: "lib/server는 서버 전용입니다. 양쪽에서 쓰는 순수 코드는 lib/shared로 옮기세요.",
};

export default defineConfig([
  {
    files: ["components/**", "lib/client/**", "lib/shared/**"],
    ignores: ["**/*.test.ts", "**/*.test.tsx"],
    rules: { "@typescript-eslint/no-restricted-imports": ["error", { patterns: [serverOnly] }] },
  },
]);
```

- ` allowTypeImports: true `로 타입 import는 허용한다\.
- 테스트 파일은 서버 fixture를 쓸 수 있도록 제외한다\.
- 규칙을 넣은 뒤에는 금지 import를 넣은 임시 파일로 실제로 오류가 나는지 확인한다\. 패턴이 경로와 맞지 않으면 아무것도 막지 않고 통과한다\.

` server-only ` 패키지도 같은 목적에 쓸 수 있다\. 다만 그 패키지는 잘못된 import를 build 시점에야 알려 준다\. lint 규칙은 편집기에서 바로 알려 주고 새 의존성도 필요 없다\.

### 확장 판단

다음 조건이 생기면 ` lib/server/ ` 안을 기능별로 더 나누거나 기능 중심 구조로 옮긴다\.

- ` lib/server/ ` 아래 기능 폴더가 10개를 넘는다\.
- 한 기능의 화면·client·server 파일을 함께 고치는 변경이 대부분이 된다\.
- 여러 사람이 기능 단위로 나눠 맡는다\.

다음 조건이 생기면 port 구현을 ` apps/web `에서 package로 옮긴다\.

- 같은 adapter를 쓰는 두 번째 실행 서버\(Worker 등\)가 생긴다\.

예상 재사용이나 폴더 대칭만으로는 어느 layer도 추가하지 않는다\.

### 검증

- [ ] 브라우저 쪽 폴더에서 ` lib/server ` 값 import가 lint로 막히는가
- [ ] 금지 import를 넣은 임시 파일로 lint 규칙이 실제로 동작하는지 확인했는가
- [ ] ` lib/shared `에 I/O가 없는가
- [ ] route 파일이 ` lib/server ` 함수 호출만 하는가
- [ ] package끼리 서로의 adapter를 import하지 않는가\(package 경계 스크립트\)
- [ ] use case가 의존성을 인자로 받고, 통합 테스트가 fake provider로 흐름을 증명하는가
- [ ] 폴더 이동은 ` git mv `로 해 이력이 이어지는가

lint는 import 방향만 검사한다\. &quot;이 파일이 정말 순수한가&quot;, &quot;이 로직이 route에 있어도 되는가&quot;처럼 의미에 관한 책임 경계는 리뷰에서 본다\.

### 정리

- 첫 번째 축은 기능이 아니라 실행 위치다\. ` app `은 진입점, ` components `·` lib/client `는 브라우저, ` lib/shared `는 순수 공용 코드, ` lib/server `는 서버 전용이다\.
- 서버 안은 port\(계약\)·adapter\(구현\)·use case\(조립\)·composition root\(주입\)로 나누되, 클래스와 컨테이너 없이 함수와 인자로 구현한다\.
- 방향 규칙은 lint로 강제하고, 규칙이 실제로 오류를 내는지 확인한다\.
- 기능 중심 구조로의 전환은 기능 수와 협업 단위가 실제로 커질 때 판단한다\.

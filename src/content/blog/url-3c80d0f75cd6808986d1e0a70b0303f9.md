모바일에서 사전서명 URL로 이미지를 직접 업로드할 때, 서버 내부에서는 접근 가능한 주소가 단말에서는 해석되지 않을 수 있다\. 이 문제는 화면 서버 접속과 별개이며, 서명된 URL을 클라이언트에서 치환하는 방식으로 해결해서는 안 된다\.

S3 호환 객체 저장소와 Docker 네트워크를 예로 들어 URL을 발급하는 서버와 소비하는 단말의 네트워크 경계를 살펴본다\. 주소·서비스명·버킷명은 모두 가상 예시다\.

큰 파일을 백엔드로 중계하지 않고 저장소로 직접 전송하면 백엔드가 파일 전송을 처리하는 부담을 분리할 수 있다\.

```text
클라이언트 → 백엔드: 업로드 세션 요청
백엔드 → 클라이언트: 사전서명 URL과 headers
클라이언트 → 객체 저장소: 이미지 PUT
```

마지막 PUT의 실행 주체는 서버가 아니라 단말이다\. 따라서 URL은 단말이 접근할 수 있는 주소여야 한다\.

### 내부 주소가 노출되는 경우

백엔드와 저장소가 같은 Docker 네트워크에 있다면 서비스명으로 서로 접근할 수 있다\. 예를 들어 다음 주소는 그 네트워크 안에서만 해석되는 주소일 수 있다\.

```text
http://object-store:9000/example-bucket/uploads/example
```

백엔드가 이 내부 endpoint를 그대로 사용해 사전서명 URL을 만들면 단말도 object\-store라는 호스트에 연결하려 한다\. 단말은 Docker 내부 DNS를 사용하지 않으므로 호스트를 찾지 못할 수 있다\.

iOS에서 호스트 이름을 찾을 수 없다는 오류가 발생한다면 먼저 실패한 요청이 화면 로드인지, 객체 저장소 PUT인지 구분해야 한다\.

### 화면이 열려도 업로드가 실패하는 이유

화면 서버 URL과 업로드 URL은 별개다\. 개발 환경에서 화면 URL을 단말이 접근 가능한 주소로 바꾸는 처리가 있더라도, 업로드 URL까지 같은 방식으로 처리할 수 있다는 뜻은 아니다\.

화면 로드가 성공했다는 사실은 객체 저장소의 DNS·포트·네트워크 접근성을 증명하지 않는다\. 실패한 PUT의 URL과 발급 경로를 확인하되 사전서명 URL 원문은 로그에 남기지 않는다\.

### 클라이언트에서 host를 바꾸면 안 되는 이유

사전서명 요청은 host를 포함한 서명 대상 값과 일치해야 한다\. 내부 host를 외부 주소로 바꾸면 서명 검증이 실패해 403이 발생할 수 있다\.

```text
발급: 내부 endpoint로 서명된 URL
변경: 클라이언트가 host를 외부 endpoint로 치환
결과: 요청과 서명 대상 불일치
```

클라이언트는 발급된 URL과 headers를 그대로 사용한다\. 접근 불가능한 주소를 받았을 때 임의로 보정하는 로직을 추가하지 않는다\.

### 확인할 설정과 경계

서명 URL 생성 경로에서 클라이언트가 접근 가능한 endpoint를 사용해야 한다\. 내부 통신 주소와 외부 발급 주소가 어떻게 선택되는지 백엔드·저장소 설정을 함께 확인한다\.

예를 들어 외부에서 접근할 수 있는 endpoint를 다음처럼 구성할 수 있지만, 주소 교체만으로 설정이 완료됐다고 판단할 수는 없다\.

```text
https://storage.example.com/example-bucket/uploads/example
```

설정 수정 여부와 실제 단말 PUT 성공 여부는 각각 확인해야 한다\. 클라이언트 코드만 보고 서버 설정이 반영됐거나 수정 범위가 작다고 단정하지 않는다\.

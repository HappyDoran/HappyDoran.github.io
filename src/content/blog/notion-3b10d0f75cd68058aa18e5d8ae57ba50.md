### 문서 목적

Native image lifecycle, Web orchestration, object storage upload와 asynchronous analysis request의 책임 분리를 설명한다\. Field\-level contract는 ` 랜드마크 기반 이미지 분석 API 계약 ` 문서를 기준으로 한다\.

### 2\. Native capture lifecycle

1. Camera 또는 photo picker에서 source image 확보
1. Orientation을 ` up `으로 정규화
1. 최대 dimension 2048px JPEG 생성
1. 12 landmark mapping과 waist point derivation
1. Overlay에서 manual adjustment 반영
1. SHA\-256, byte size, dimensions 생성
1. ` capture_<uuid> ` 발급
1. Temporary file registry에 24시간 TTL로 저장
1. Web에 metadata, preview와 landmarks 반환

` file:// ` path는 result contract에 포함하지 않는다\.

### 3\. Bridge 흐름

```text
REQUEST_POSE_CAMERA
  -> Native open()
  -> POSE_CAMERA_COMPLETED | CANCELLED | ERROR

REQUEST_CAPTURE_IMAGE_UPLOAD
  -> Native uploadCapture(captureId, url, method, headers)
  -> CAPTURE_IMAGE_UPLOAD_COMPLETED | FAILED
```

App과 Web은 동일한 Zod schema로 result shape를 검증한다\. Async upload response는 ` captureId `와 ` uploadId `가 모두 일치할 때만 pending Promise를 완료한다\.

### 4\. Web orchestration

` prepareBodyAnalysis `의 상태 순서:

```text
CAPTURE_READY
  -> REQUESTING_UPLOAD_URL
  -> UPLOADING_IMAGE
  -> SUBMITTING_ANALYSIS
  -> PROCESSING
  -> COMPLETED | FAILED
```

Current Mock mode:

1. Mock upload\-session response 생성
1. Native PUT 생략
1. Submit request builder 실행
1. Mock analysis response 생성
1. Result Activity로 이동

Future HTTP mode:

1. upload\-session API 호출
1. Native PUT bridge 요청
1. analysis API 호출
1. status query 또는 stream 연결

### 6\. Temporary file와 release

Native registry는 stale file을 24시간 이후 정리한다\. ` releaseCapture(captureId) ` method는 구현되어 있으나 Web success flow에서 호출하는 연결은 pending이다\.

Release policy를 연결할 때 확인:

- upload success 직후 삭제 여부
- analysis submit failure 시 retry를 위한 유지 여부
- app restart 후 recovery 여부
- storage upload expiration과 local TTL 관계

### 8\. Concurrency

- Upload Promise는 request의 two identifiers로 다른 response를 무시한다\.
- Default timeout은 60초다\.
- Native registry lookup과 upload는 local file 존재를 다시 확인한다\.
- Web loading Activity는 ` hasStartedRef `로 initial duplicate execution을 차단한다\.
- Navigation lock은 transition 중 중복 route action을 차단한다\.

### 9\. Security

- Signed URL과 header는 response 그대로 사용하고 client가 임의 변경하지 않는다\.
- Local path와 original Base64를 Web/API payload에 포함하지 않는다\.
- Server는 client status/ETag를 신뢰하지 않고 object를 검증한다\.
- Endpoint example, object key와 retention은 proposal로 유지한다\.
- Secret과 access token을 log 또는 document example에 기록하지 않는다\.

### 10\. Validation checklist

- [ ] App/Web camera result schema가 동일한가
- [ ] Landmark ID와 배열 순서가 양 플랫폼에서 동일한가
- [ ] Orientation/mirror와 coordinate space가 일치하는가
- [ ] Upload response가 request identifiers와 매칭되는가
- [ ] Mock mode에서 Native PUT가 호출되지 않는가
- [ ] HTTP mode에서 signed header가 손실되지 않는가
- [ ] Non\-2xx와 timeout이 ` FAILED `로 수렴하는가
- [ ] Release와 retry policy가 충돌하지 않는가
- [ ] OpenAPI 확정 후 proposal field와 diff를 검토했는가

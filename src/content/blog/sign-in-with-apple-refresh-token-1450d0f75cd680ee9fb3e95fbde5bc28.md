앱 시작 시 저장된 세션을 복원할지, Sign in with Apple을 실행할지, 추가 가입 정보를 받을지 결정해야 한다\. 인증 상태와 화면 상태를 분리하고 토큰 갱신·저장·화면 이동의 순서를 정리한다\.

### 진입 상태

초기 상태를 복원 중, 로그인 필요, 인증 완료로 나눌 수 있다\. 특정 화면 이름을 인증 상태로 사용하기보다 서버 세션이 준비됐는지를 기준으로 분기한다\.

### Apple 로그인과 서버 인증

Apple 인증 결과의 Identity Token·Authorization Code·사용자 식별 정보를 서버 요청 계약에 맞게 전달한다\. 서버는 기존 사용자와 추가 가입이 필요한 사용자를 구분해 응답한다\.

특정 HTTP 200·201을 모든 서버의 공통 가입 판정으로 해석하지 않는다\. 사용자 정보·토큰·추가 입력 여부를 서버가 어떤 응답으로 표현하는지 계약을 먼저 정한다\.

기존 사용자라면 응답의 Access Token과 Refresh Token을 Keychain에 저장하고 사용자 상태를 갱신한 뒤 인증 완료 화면으로 이동한다\.

추가 가입이 필요하면 입력 화면으로 이동한다\. 이메일·닉네임 같은 추가 입력을 서버로 보내 가입을 마치고, 응답에서 발급한 토큰을 저장한 뒤 같은 인증 완료 경로로 합류한다\.

### NotificationCenter의 역할

로그인이나 가입 후 여러 화면이 사용자 정보 변경을 알아야 한다면 NotificationCenter를 상태 변경 알림으로 사용할 수 있다\. 발행자와 구독자가 같은 알림 이름·payload 계약을 사용해야 한다\.

알림을 보내는 것과 데이터를 저장하는 것은 다르다\. 토큰 저장·사용자 상태 갱신을 마친 뒤 알림을 보내고, 구독자는 필요한 상태를 다시 읽거나 전달된 값을 처리한다\.

원문의 사용자 정보 채널을 생성한다는 메모는 이 상태 변경 통지 역할로 해석했다\. 정확한 payload와 구독 화면은 코드가 제시되지 않아 구체화하지 않는다\.

### 앱 시작 시 토큰 판정

토큰과 만료 시각을 함께 보관한다면 다음 흐름으로 진입을 결정할 수 있다\.

```text
Access Token이 유효함
  → 인증된 진입 경로

Access Token 갱신이 필요함
  → Refresh Token 확인
      → 사용 가능: 갱신 요청 → 새 토큰 저장 → 인증된 진입 경로
      → 없음·사용 불가: 로그인 경로
```

서버의 응답을 통한 세션 복원 정책을 선택할 수도 있다\. 로컬의 만료 계산만으로 서버 세션의 유효성까지 확정하지 않는다\.

### 사용 중 갱신

인증 요청이 Unauthorized를 반환하면 토큰 갱신이 필요한 상황인지 판단한다\. Refresh Token으로 새 토큰을 받고 Keychain을 갱신한다\.

갱신 실패를 모두 같은 이유로 숨기지 말고, 사용할 수 없는 세션과 요청 오류의 처리 방식을 계약으로 정한다\. 원문의 질문형 메모만으로 서버의 상세 오류 정책까지 확정하지 않는다\.

### 필요한 책임

- 토큰 이름·값·만료 시각을 표현하는 모델
- Keychain에서 두 토큰을 읽고 저장하는 함수
- 만료 시각을 판단하는 함수
- Refresh Token으로 세션을 갱신하는 함수
- 인증 결과를 사용자 상태와 화면 이동에 반영하는 경로

완료 표시 대신 역할별 점검 목록으로 관리한다\. 등록·가입·자동 로그인 모두가 같은 저장·상태 갱신 경로를 사용하면 흐름을 추적하기 쉽다\.

### 정리

앱 진입은 토큰 읽기, 세션 복원, 필요한 로그인·가입, 인증 완료로 나눈다\. 특정 화면명이나 상태 코드보다 서버 계약을 기준으로 분기하고, 토큰 저장·상태 변경 알림·화면 이동의 순서를 명확히 한다\.

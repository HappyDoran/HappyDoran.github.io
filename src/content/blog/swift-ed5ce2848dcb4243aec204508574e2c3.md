Swift 네트워크 계층을 리뷰할 때는 파일 이름보다 요청 구성·전송·응답 처리의 책임이 분리됐는지 보는 편이 유용하다\. HTTP method, URLComponents, Router, 제네릭 데이터 처리라는 관점으로 점검 항목을 정리한다\.

### HTTP method와 문자열 표현

GET·POST 같은 method를 타입으로 정의하면 요청마다 문자열을 반복하는 범위를 줄일 수 있다\. 문자열 보간으로 method를 표시하는 구현이라면 CustomStringConvertible을 통해 어떤 값으로 변환되는지 확인한다\.

### URLComponents로 URL 구성

scheme·host·port·path·query를 URLComponents에 모으고 최종 URL을 만든다\. Router가 필요한 값을 제공하고 URL 조립의 공통 책임은 한 곳에서 관리하는 구조다\.

요청마다 query가 필요한지 확인한다\. query가 없는 요청에 임의 값을 넣기보다 해당 계약에 맞는 nil·빈 값 처리를 명확히 한다\.

### 프로토콜 요구사항과 기본 구현

프로토콜은 필요한 메서드·프로퍼티 요구사항을 선언하고 extension은 기본 구현을 제공할 수 있다\. 프로토콜에는 함수나 연산 프로퍼티를 전혀 정의할 수 없다는 식으로 구분하지 않는다\.

URL 구성 계약과 요청 구성 계약을 분리했다면 요청 계약이 URL 구성 책임을 어떻게 사용하는지 확인한다\.

### URLRequest 생성

```swift
var request = URLRequest(url: url)
request.httpMethod = "\(httpMethod)"
request.allHTTPHeaderFields = headerFields
```

이 코드는 URL·method·header를 결합하는 경계다\. 각 값이 Router에서 어떤 경로로 오는지 추적할 수 있어야 한다\.

JSON 요청에는 해당 계약에 맞는 header가 필요하다\. 모든 요청을 같은 방식으로 처리한다고 가정하지 말고 method·body·query·header 차이를 확인한다\.

### Router와 환경 설정

Router는 요청 종류를 enum case로 나누고 필요한 parameter를 받도록 구성할 수 있다\. 개별 기능의 이름보다 각 case가 어떤 method·path·query를 만드는지 검토한다\.

기본 host는 환경 설정에서 관리할 수 있다\. 설정 파일을 Git에서 제외했다는 사실만으로 요청 구성과 공개 범위가 모두 안전해졌다고 판단하지 않는다\.

제네릭 함수가 범용성을 제공하더라도 요청 구성과 응답 변환이 어디서 수행되는지는 숨기지 않는다\. 외부에 노출한 함수와 내부 처리 흐름의 역할을 설명할 수 있어야 한다\.

### 정리

- method·URL·header의 생성 책임을 추적한다\.
- URLComponents와 Router의 경계를 확인한다\.
- 프로토콜 요구사항과 extension 기본 구현을 구분한다\.
- 제네릭 요청·응답 처리의 공개 계약과 내부 실행 책임을 나눈다\.

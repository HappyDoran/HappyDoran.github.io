## MVVM의 문제점

- MVVM 패턴은 View의 상태와 동작을 분리해서 View가 비즈니스 로직을 직접 다루지 않고 데이터만 얻을 수 있도록 해줍니다\.
- 각 View 마다 ViewModel이 생성되고 각각의 ViewModel은 ` ObservableObject ` 프로토콜을 준수합니다\. 이는 SwiftUI에서 제공하는 SOT와는 별개로 새로운 SOT를 정의하는 것이기 때문에 불필요한 복잡도를 만듭니다\.
- ViewModel의 주요 역할인 바인딩은 SwiftUI의 프로퍼티 래퍼로 View 내에서 가능하기 때문입니다\.

→ MVVM을 사용하여 화면마다 ObservableObject를 추가하는 것은 ` 불필요한 SOT를 추가 `하고 ` 복잡성을 증가 `시킵니다\.

## MV 패턴

Apple이 SwiftUI앱의 샘플 코드에서 사용하는 것과 동일한 패턴입니다\. 누구는 상태 패턴이라 부르고… 누구는 Model View 패턴이라 부른다는데… 아무튼 MV 패턴의 기본 아이디어는 사용자가 상태를 변경, 변형하는 작업을 수행하면, 뷰가 다시 랜더링 됩니다\. 이 작업을 일정한 루프에서 실행합니다\. 상태를 변경하는 작업을 할 때마다 새 버전의 뷰가 생성되어 화면에 랜더링됩니다\. 

![](<../../assets/blog/mv-c31333e32a8e43df896ec0b6ee12c550/image-001.png>)

해당 그림에서 State는 Model에서 데이터를 가져와 View에 직접 제공합니다\. 액션은 버튼을 누르거나 외부 이벤트로 트리거가 될 수 있습니다\. 

![](<../../assets/blog/mv-c31333e32a8e43df896ec0b6ee12c550/image-002.png>)

MVVM의 문제점으로 MV 패턴이 등장했는데, 각각의 MV 혹은 레이어는 별도의 SPM으로 분리될 수 있습니다\.

## MV layer

### Aggregate Root

Aggregate Root의 주요 개념은 하나의 관찰 가능한 객체가 모델 객체에 액세스 하는 게이트웨이 역할을 한다는 것입니다\. 모든 모델은 Swift에서 구조체 데이터 타입을 사용하여 구현된 값 타입이 됩니다\. 이렇게 하면 앱에 모든 로직을 위한 하나의 장소가 제공됩니다\. 

![](<../../assets/blog/mv-c31333e32a8e43df896ec0b6ee12c550/image-003.png>)

이러한 Aggregate Root Model은 SwiftUI에서 ` @EnvironmentObject ` 를 사용하여 글로벌 객체로 주입될 수도 있습니다\. 객체는 단순히 관찰 가능한 객체로, 외부 서비스\(네트워크 계층\)와 통신하여 데이터를 뷰로 가져올 수 있습니다\.

![](<../../assets/blog/mv-c31333e32a8e43df896ec0b6ee12c550/image-004.png>)

더 복잡한 앱의 경우, 애플리케이션의 ` bounded context `에 따라서 여러 Aggregate Root 객체를 도입할 수도 있습니다\.

### Aggregate Root

```swift
@MainActor
class Store: ObservableObject {
    
    @Published var products: [Product] = []
    
    func loadProducts() async throws {
        products = try await Webservice.shared.fetchProducts()
    }
    
    func addProduct(_ product: Product) {
        // code...
    }
    
    func loadCart() {
        // code...
    }
    
    func loadUsers() {
        // code...
    }
    
    func addProduct() {
        // code ...
    }
    
}
```

언뜻 보게 되면 Store는 그저 이름이 다른 ViewModel로 보일 수 있습니다\. 하지만 Store는 ViewModel이 아니고 앱이 모델 객체에 접근할 수 있도록 하는 Aggregate Root 입니다\. **화면당 별도의 ViewModel을 만들지 않고 View에서 Store를 직접 사용하여 필요한 데이터를 가져올 수 있습니다\.** 모든 뷰에서 Store에 쉽게 접근할 수 있게 하려면 ` @EnvironmentObject ` 를 사용하면 됩니다\.

> 더 큰 앱의 경우 글로벌 상태를 여러 슬라이스로 나눌 수 있습니다\.

어떤 경우에는 별도의 Store 계층 없이 Webservice를 직접 사용하여 뷰 내에서 바로 호출할 수 있습니다\.

```swift
@MainActor
class Webservice: ObservableObject {
    
    @Published var products: [Product] = []
    
    func loadProducts() async throws {
        
        let (data, response) = try await URLSession.shared.data(from: URL(string: "https://fakestoreapi.com/products")!)
        guard let httpResponse = response as? HTTPURLResponse,
              httpResponse.statusCode == 200
        else {
            throw NetworkError.badRequest
        }
        
        products = try JSONDecoder().decode([Product].self, from: data)
        
    }
    
    func addProduct(_ product: Product) {
        // code...
    }
    
    // This can be moved to CartService 
    func loadCart() {
        // code...
    }
    
    // This can be moved to UserService
    func loadUsers() {
        // code...
    }
    
    // This can be moved to ProductService 
    func addProduct() {
        // code ...
    }
    
}
```

앱에 여러 개의 bounded context가 있는 경우에 하나의 단일 웹서비스는 각 bounded context에 맞는 여러 서비스로 나뉩니다\. 즉 단일 웹 서비스 클래스 대신에 **AccountService** , **UserService** , **ProductService** 등이 있을 수 있습니다\.

### View

- MV 패턴의 View는 기존 MVVM 패턴에서의 View \+ ViewModel의 역할을 합니다\.
- View에서 Model은 ` @EnvironmentObject `, ` @StateObject `, ` @ObservedObject `를 통해 사용됩니다\.
- View에 한정된 프로퍼티는 View 내에 ` @State `와 ` @Binding `으로 만듭니다\.
- View에 한정된 로직은 View 내에 함수나 연산 프로퍼티로 만듭니다\.

```swift
import SwiftUI

@main
struct LearnApp: App {
    
    @StateObject private var store = Store()
    
    var body: some Scene {
        WindowGroup {
            ContentView().environmentObject(store)
        }
    }
}
```

```swift
struct ContentView: View {
    
    @EnvironmentObject private var store: Store
    
    private func populateProducts() async {
        do {
            try await store.loadProducts()
        } catch {
            print(error.localizedDescription)
        }
    }
    
    var body: some View {
        List(store.products) { product in
            Text(product.title)
        }.task {
            await populateProducts()
        }
    }
}
```

이처럼 View에서는 Store를 사용하여 모델 객체를 가져온 다음에 화면에 직접 바인딩합니다\. View와 Model 사이에는 ViewModel이 필요하지 않습니다\. 

View가 너무 커지는 것이 걱정된다면, ViewState나 Reusable 뷰를 통해 어느정도 해소할 수 있습니다\.

#### ViewState

View 내의 프로퍼티나 로직이 많이 필요할 때 사용할 수 있습니다\.

View 관련 내용을 테스트 하기에도 용이합니다\.

ViewState는 하나의 @State 프로퍼티로 만들어주면 됩니다\.

```swift
struct ExampleView: View {
    @State private var state = ExampleState()
    ...
}

struct ExampleState {
    var name = ""
    var exampleName = ""
    var errors = ExampleError()
    
    mutating func isValid() -> Bool {
        if name.isEmpty {
            errors.name = "Name cannot be empty!"
        }
        
        if exampleName.isEmpty {
            errors.exampleName = "Coffee name cannot be empty"
        }
        
        return errors.name.isEmpty && errors.exampleName.isEmpty
    }
}
```

#### Reuseable 뷰

재사용이 가능한 컴포넌트 뷰

```swift
enum Events {
    case onChecked(Int)
    case onDelete(Int)
}

struct ContainerScreen: View {
    var body: some View {
        List(1...20, id: \.self) { index in
            PresenterView(index: index) { event in
                switch event {
                    case .onChecked(let index):
                        print(index)
                    case .onDelete(let index):
                        print(index)
                }
            }
        }
    }
}

struct PresenterView: View {
    let index: Int
    let onEvent: (Events) -> Void
    
    var body: some View {
        HStack {
            Image(systemName: "square")
                .onTapGesture {
                    onEvent(.onChecked(index))
                }
            Text("\(index)")
            Spacer()
            Image(systemName: "trash")
                .onTapGesture {
                    onEvent(.onDelete(index))
                }
        }
    }
}
```

다음과 같이 Container 패턴을 사용하면 재사용성있는 뷰를 사용할 수 있습니다\.

View는 Container 혹은 Presenter 중 하나이고, Container는 데이터를 fetch, filter 하는 등의 로직을 가지고 있습니다\. Presenter는 어디서든 재사용 가능하게 model이 아닌 부모 뷰로부터 데이터를 전달 받아야합니다\.

→ 어디서 들었는지 모를 Container 패턴은 보통 React에서 Component를 분리할 때 사용하던 것과 동일해 보입니다\.

## Service layer

Service layer는 데이터 접근 레이어로 API 서비스 등이 있을 수 있습니다\. Service에 포함될 네트워크 레이어도 이에 해당합니다\.

```swift
class Webservice {
    
    static let shared = Webservice()
    
    private init() { }
    
    func fetchProducts() async throws -> [Product] {
        
        // The URL can be placed in a configuration so it can be changed between dev/test/prod
        let (data, response) = try await URLSession.shared.data(from: URL(string: "https://fakestoreapi.com/products")!)
        guard let httpResponse = response as? HTTPURLResponse,
              httpResponse.statusCode == 200
        else {
            throw NetworkError.badRequest
        }
        
        return try JSONDecoder().decode([Product].self, from: data)
    }
    
}
```

> 다양한 환경간에 전환할 수 있도록 웹 서비스 클래스에 구성 옵션을 추가할 수 있습니다\.

### Extract as ViewState

위에서 ViewState를 따로 빼놓은 것은, 코드 분리도 되고 testable 하게 하기 위함도 있습니다\.

아래처럼 Unit Test를 작성할 수도 있습니다\.

```swift
import XCTest
@testable import ExampleApp

class ExampleAppTests: XCTestCase {
    func testExampleStateValidationSuccess() {
        var state = ExampleState(name: "John Doe", exampleName: "SwiftUI")
        XCTAssertTrue(state.validate(), "Validation should pass when all fields are provided.")
    }
    
    func testExampleStateValidationFailure() {
        var state = ExampleState()
        XCTAssertFalse(state.validate(), "Validation should fail when fields are empty.")
        XCTAssertEqual(state.errors.name, "Name cannot be empty!")
        XCTAssertEqual(state.errors.exampleName, "Example name cannot be empty!")
    }
}
```

### E2E test

End\-to\-end 테스트는 UI 테스트입니다\.

```swift
import XCTest

class ExampleAppUITests: XCTestCase {
    func testExampleViewInteraction() {
        let app = XCUIApplication()
        app.launch()
        
        let nameField = app.textFields["Name"]
        let exampleNameField = app.textFields["Example name"]
        
        nameField.tap()
        nameField.typeText("John Doe")
        
        exampleNameField.tap()
        exampleNameField.typeText("SwiftUI")
        
        app.buttons["Update"].tap()
        
        XCTAssertTrue(app.staticTexts["Update Successful"].exists)
    }
}
```

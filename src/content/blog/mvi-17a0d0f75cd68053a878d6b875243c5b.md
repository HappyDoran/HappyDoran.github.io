## <strong>MVI 등장 배경 / 필요성</strong>

### SwiftUI에서의 MVVM 패턴

Model, View, ViewModel로 이루어진 구성의 아키텍쳐 패턴\.

### ViewModel

- View의 이벤트와 그에 대한 액션을 바인딩
- View에서 어떠한 이벤트를 ViewModel에 전달해주면, 이벤트의 본체가 ViewModel에 구현이 되어 있고, 이벤트에 대한 처리, 그 결과로 수행할 액션을 다시 ViewModel에 전달\.

![](<../../assets/blog/mvi-17a0d0f75cd68053a878d6b875243c5b/image-001.png>)

이렇게 양방향 데이터 플로우로 구성이 되어있는 MVVM 패턴은,
SwiftUI에서는 어차피 바인딩 처리로 이벤트를 처리하기 때문에 굳이? 라는 생각이 든다\. 

→ <strong>SwiftUI는 단방향 데이터 플로우를 기반으로 한다\.</strong>

그리고 이렇게 양방향 데이터 플로우의 ViewModel 에서 너무 많은 일을 하고 있기 때문에 ViewModel이 더러워진다\. 

그렇기 때문에 단방향 데이터 플로우로 흐름을 이해하고 관리하기 쉽게 하기 위해 MVI 패턴이 등장한다\.

## MVI 패턴

Model, View, Intent로 이루어진 구성의 아키텍쳐 패턴\. 얘기 들어보니까 뭐 SwiftUI에서 TCA 패턴을 많이 쓰는데 그걸 라이브러리 의존성 없이 간소화한 것이라고 하더라\.

### Model

앱의 상태를 나타내는 데이터 모델

Intent로부터 데이터를 받아서 UI로 보여주기 위해 준비하고, 가장 최근의 상태\(현재 상태\)를 가진다\.

항상 View의 현 상태를 유지\(State == Model\) 한다\. 

Model은 View에게 상태 변경을 알려줘야 하기 때문에 View를 참조한다\.

### View

전달받은 Model\(상태\)로 UI를 보여준다\.

View는 사용자 입력이나 이벤트가 발생했을 때 이를 Intent에게 알려주어야 한다\. 따라서 View에서는 Intent 메서드를 호출할 수 있어야 하므로 Intent를 참조한다\.

### Intent

View에서 이벤트를 받아서 이벤트를 실질적으로 하는 비즈니스 로직을 실행, 라이프 사이클에 따른 실행을 한다\.

Intent는 비즈니스 로직을 실행한 후 Model의 상태를 업데이트 해야 한다\. 따라서 Intent는 Model을 참조하여 상태를 변경한다\.

> ❓ <strong>여기서 의문점</strong>
> 
> Model이랑 Intent는 로직과, 실제 보여질 데이터를 가지고 있으면 class\. 즉 참조 타입일테고, View는 struct\. 값 타입일텐데, Model은 어떻게 View에 대한 참조를 가질 수 있을 것인가?

### Container

따라서 View에서는 Container라는 개념이 존재한다\. Intent와 Model은 컨테이너에 담겨서 View에서 instance를 들고 있다\.

→ Intent와 Model에 대한 참조를 관리하고 접근성을 제공해주는 역할\. View 생성시 Container를 포함

![](<../../assets/blog/mvi-17a0d0f75cd68053a878d6b875243c5b/image-002.png>)

즉 다음과 같은 흐름이 탄생한다\.

간략하게 설명하자면,

<strong>Model, ModelStateProtocol, ModelActionsProtocol</strong>
→ view에서 보여질 상태와 intent에서 실행할 model의 action을 정의한다\.

<strong>IntentProtocol, Intent</strong>
→ view에서 event가 발생 했을 때 실행할 비즈니스 로직을 구현한다\.

<strong>MVIContainer, View</strong>
→ Model과 Intent를 포함하는Container를 생성하고, 연결한다\.

## MVI 패턴은 왜 등장했나?

MVI 패턴은 MVVM에서 발생하는 <strong>상태 관리 문제</strong>와, <strong>부수 효과</strong>라는 두가지 문제를 해결하기 위해 탄생했다\.

### 상태 관리

MVVM 패턴에서는 상태가 여러개의 ViewModel에 분산되어 있을 수 있다\. 이는 상태 변경이 여러 곳에서 일어나기 때문에, 예기치 않은 방식으로 상태가 변할 수 있는 문제가 발생한다\.

어플리케이션이 커질 수록 상태가 분산되어버리고, 여러 곳에서 변경될 수 있기 때문에 일관성있게 유지하는게 어려워진다\.

MVI 에서의 상태는 <strong>불변</strong>이기 때문에 View → Intent → Model → View가 상태를 변경할 수 있는 유일한 방법이다\.

이는 SwiftUI의 본연의 데이터 흐름과 많이 흡사하다\. \(함수형 프로그래밍\)

![](<../../assets/blog/mvi-17a0d0f75cd68053a878d6b875243c5b/image-003.png>)

### 부수 효과

MVVM 패턴에서 서버 호출, 데이터 베이스 접근 등 비동기 작업을 진행할 때 언제 완료 될지 모르기 때문에 상태 변경을 예측하기 어렵습니다\.\(근데 이건 어떤 패턴에서든지 똑같지 않나…\)

예를 들어서 네트워크 요청을 하고 상태가 변경될 때 다른 부분의 상태도 변경이 될 수 있다\.

MVI의 경우 이런식으로 Side effect\(네트워크 요청과 같은 작업\)를 할 때 새로운 상태를 생성하고, Side Effect를 실행한다\. 실행이 끝나면 바로 render를 하는게 아닌 Event로서 결과를 전달한다\.

![](<../../assets/blog/mvi-17a0d0f75cd68053a878d6b875243c5b/image-004.png>)

## GCD

### 노동자\(Thread\)에게 일\(Task\)을 분배해보자

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-001.png>)

우리의 컴퓨터에는 많은 노동자\(Thread\)들이 있습니다\. 이 노동자들에게 일\(Task\)를 잘 분배해야 효율적으로 코드를 작성할 수 있습니다\.

### 일을 잘 나눠보자

메인 스레드에 몰린 작업들을 다른 스레드에서도 작업하도록 하는 것 

그러한 작업을 이제 동시로 하게 된다면 이게 동시성 프로그래밍이 되는겁니다\.

#### 그럼 일은 이제 누가 나누나요?

ios에서는 작업을 한곳으로 보내기만 하면 알아서 OS가 다른 스레드로 분산 처리를 해줍니다\.

그럼 어디로 보내냐? Queue\(대기행렬\)라는 곳으로 보냅니다\.

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-002.png>)

→ 그럼 우리가 할일은 작업을 큐로 보내는 것\. 이게 다입니다\.

### GCD\(Grand Central Dispatch\)

우리가 Task를 Queue로 작업을 보내면, 작업을 수행하는 스레드를 적절히 생성해서 분배를 해주는 방법

GCD에서 사용하는 Queue의 이름이 Dispatch Queue인겁니다\.

→ Dispatch Queue에 내가 수행하고자 하는 여러 Task를 추가하면 작업에 맞는 Thread를 자동으로 생성해서 실행하고 작업이 끝나면 Thread를 제거하는거까지 해줍니다\.

```swift
DispatchQueue.global(){
  //task
}
```

- DispatchQueue: iOS에서 동시성 프로그래밍을 돕기 위해 제공하는 queue
- global: DispatchQueue의 종류

→ //task에 들어가는 작업은 하나의 작업 뭉탱이 입니다

```swift
 //작업 자체가 묶이는 개념
  print("Task1 시작")
  print("Task1 의 중간작업 1")
  print("Task1 의 중간작업 2")
  print("Task1 의 중간작업 3")
  print("Task1 의 중간작업 4")
  print("Task1 의 중간작업 5")
  print("Task1 종료")
  //이거 전체가 //task에 다 들어가는겁니다.
```

## Async\(비동기\) &amp; Sync\(동기\)

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-003.png>)

이와 같이 Main Thread에서 혼자 일 안하고 다른 Thread에 일을 보내기 위해 Queue에 보낸다 해보자\.

Queue에 작업을 보내고 난 후에 Main Thread의 행동은 어떨까요?

### 1\. 신경 끄고 자기한데 쌓여있는 일을 한다\(비동기\)

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-004.png>)

#### 비동기

queue에 보낸 작업에 대해서는 더이상 신경쓰지 않고, 바로 다른 일을 해버립니다\.

```swift
DispatchQueue.global().async {
  //task
}
```

해당 코드를 말로 풀어서 쓰면, 이렇습니다\.

→ 원래의 작업이 진행되고 있던 Main Thread에서 global dispatch queue로 task를 보낸 후, 해당 작업이 끝나기를 기다리지 않고 이어서 할 일을 합니다\.

#### 결론

Main Thread가 작업을 Queue에 던졌다? 

그게 1초가 걸리는 작업이던, 1시간이 걸리던 작업이던 신경 쓰지 않는다\.

### 2\. 끝날 때까지 기다린 후에 자기한테 쌓인 일을 한다\(동기\)

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-010.png>)

#### 동기

어떤 작업을 Queue로 보낸 뒤 해당 작업이 완료될 때까지 기다린 후 다음 줄로 넘어갑니다\.

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-011.png>)

해당 작업들을 다 처리하기까지는 6초가 좀 더 걸립니다\.

#### 왜 비동기 처리가 필요한가요?

비동기로 처리했을 때 위에서 보던 것처럼 시간 절약이 체감이 확됩니다\. 시간이 많이 드는 작업의 대부분은 서버와의 통신이기 때문에, 네트워킹과 관련된 작업들은 내부적으로 비동기적으로 구현되어있습니다\.

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-012.png>)

## Serial\(직렬\) &amp; Concurrent\(동시\)

이제 Queue에 쌓여있는 Task를 다른 Thread로 내보내는 방식에 대해 알아보겠습니다\.

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-013.png>)

### 1\. 한개의 Thread에 몰아 넣는다\(Serial\)

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-014.png>)

Serial 큐에 담긴 작업들은 오직 하나의 Thread에 분배가 되기 때문에 각 task의 시작과 종료에 대한 순서 예측이 가능합니다\.

→ 순서가 중요한 작업들을 처리한다고 하면 SerialQueue를 사용하는게 좋습니다\.

### 2\. 여러개의 Thread에 나눈다\(Concurrent\)

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-015.png>)

Concurrent 큐에 담긴 작업들은 여러 Thread에 분배됩니다\. 따라서 그들이 끝나는 순서는 알 수 없습니다\.

→ 각 cell에서 이미지를 로드한다 하면 어떤 데이터가 먼저 들어와야할지 순서는 중요하지 않습니다\. 그냥 빠르면 좋은거니까 이상황에서는 ConcurrentQueue를 사용하는게 좋습니다\.

### 그렇다면 정리

` SerialQueue.sync ` : 메인 스레드의 <strong>작업 흐름</strong>이 queue에 넘긴 태스크가 끝날때까지 <strong>멈춰있고</strong>\(` sync `\), 넘겨진 task는 queue에 <strong>먼저 담겨있던 작업</strong>들과 <strong>같은 스레드</strong>에 보내지기 때문에 해당 작업들이 모두 <strong>끝나야 실행</strong> \(` Serial Queue `\)

` ConcurrentQueue.sync ` : 메인 스레드의 <strong>작업 흐름</strong>이 queue에 넘긴 태스크가 끝날때까지 <strong>멈춰있고</strong>\(` sync `\), 넘겨진 task는 queue에 <strong>먼저 담겨있던 작업</strong>들과 <strong>다른 스레드</strong>에 보내질 수 있기 때문에 해당 작업들이 모두 <strong>끝나지 않아도 실행</strong> \(` Concurrent Queue `\)

` SerialQueue.async ` : 메인 스레드의 <strong>작업 흐름</strong>이 태스크를 queue에 넘기자마자 <strong>반환</strong>되고 \(` async `\), 넘겨진 task는 queue에 <strong>먼저 담겨있던 작업</strong>들과 <strong>같은 스레드</strong>에 보내지기 때문에 해당 작업들이 모두 <strong>끝나야 실행</strong> \(` Serial Queue `\)

` ConcurrentQueue.async ` : 메인 스레드의 <strong>작업 흐름</strong>이 태스크를 queue에 넘기자마자 <strong>반환</strong>되고 \(` async `\), 넘겨진 task는 queue에 <strong>먼저 담겨있던 작업</strong>들과 <strong>다른 스레드</strong>에 보내질 수 있기 때문에 해당 작업들이 모두 <strong>끝나지 않아도 실행</strong> \(` Concurrent Queue `\)

#### GCD의 정리 

1. task들을 Queue로 보냄
1. 큐의 특성이 serial이냐 concurrent에 따라서 task를 하나의 스레드, 여러 스레드로 보냄

## Dispatch Queue

큐의 종류에 따라 특성이 다르기 떄문에, 작업의 특성, 원하는 일처리에 따라 큐의 특성에 맞게 작업을 넣어야 합니다\.

### 메인 큐

```swift
let mainQueue = DispatchQueue.main
```

Serial Queue

오직 한개만 존재하고, 메인 큐에 할당된 Task는 Main Thread에서 처리합니다\.

우리가 별다른 처리를 해주지 않은 코드들은 죄다 메인 스레드에서 처리되고 있었던 겁니다\.

→ 그러니까 print\(”Hello Doran”\)같은 것도 죄다 메인 스레드에서 처리되고 있었던 거에요\.

#### 어떤식으로 되는건가요 그러면?

메인큐에서의 task는 메인 스레드로만 보냅니다\. 

근데 메인 스레드는 하나밖에 없으니까 거기로밖에 task를 못보내는겁니다\.

그래서 분산 시킬려고해도 분산 시킬 수 없죠\. 강제로 serial\(직렬\)이 되버리는겁니다\.

### 글로벌 큐

```swift
let userInteractiveQueue = DispatchQueue.global(qos: .userInteractive)
let defaultQueue = DispatchQueue.global()  // 디폴트 글로벌큐
```

Concurrent Queue

여러개의 스레드로 task 분산이 가능합니다\.

→ 작업할 때 순서가 중요하지 않은 것들을 보내면 됩니다\.

따라서 qos\(작업의 중요도\)를 처리합니다\.

### Qos

#### userInterative

사용자와 <strong>직접 상호작용</strong> 하는 작업\. \(ex\. UI 업데이트, 애니메이션 등\)

사용자의 행동에 대한 즉각적인 반응이 기대 되지만, 이를 메인 스레드에서 처리하면 많은 로드가 걸리는 작업들을 userIneractive에서 처리해서 바로 동작하는 것처럼 보이게 함\.

#### userInitiated

클릭할 때 작업을 수행하는 것과 같은 <strong>즉각적인 결과</strong>가 필요한 작업\. \(ex\. 저장된 문서 열기\)

하지만 userIneractive 보다는 조금 오래걸릴 수 있고 유저가 어느정도 이를 인지하고 있음\.

#### default

<strong>일반</strong>적인 작업\.

#### utility

보통 <strong>progress bar와 함께 길게 실행</strong>되는 작업\. \(ex\. 데이터 다운로드\)

#### background

유저가 직접적으로 <strong>인지하지 않는 시간이 덜 중요</strong>한 작업\. \(ex\. 동기화 및 백업\)

#### unspecified

QoS <strong>정보가 없음</strong>을 나타냄\. 거의 사용할 일 없다\.

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-016.png>)

실제로 이 task들이 thread에 배치가 되냐면

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-017.png>)

이런식으로 배치 됩니다\.

→ qos에 대해서는 일단 이런식으로 우선순위를 나누어서 thread에 배정된 task가 작업되는지 이렇구나 하고 알고가는 수준이면 될 것 같습니다\.

### 커스텀\(프라이빗\) 큐

Serial or Concurrent

디폴트로 serial 특성을 가진 Queue입니다\. 하지만 concurrent로 설정이 가능하고 또한 qos도 설정이 가능합니다\.

## CompletionHandler

일을 비동기\(async\)로 보내놓고 신경을 안쓰고 난 내 task를 하고 있었는데, 그러면 실제 해당 작업이 언제 끝나는지는 어떻게 알까요?

→ Swift는 다른 스레드의 작업이 끝나면, 클로저를 통해 해당 시점을 알려줍니다\. 이게 바로 보통 우리가 completionHandler로 부릅니다\.

```swift
// 비동기적인 작업을 해야하는 함수는 항상 클로저를 호출할 수 있도록 함수를 설계해야 한다
func getImages(..., completionHandler: @escaping (UImage?) -> Void) {
	...
    URLSession.shared.dataTask(..) {
    	...
    	...
    	completionHandler(photoImage)	// 함수 내부의 일이 끝나면 completionHandler 호출한다
    }.resume()
}
```

### CompletionHandler의 문제점

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-018.png>)

해당 코드에서는 에러 상황에서는 completion을 호출하지 않고 바로 return을 하는 모습을 보입니다\.

→ completion을 적는지 안적는지는 개발자에게 달려있기 때문에 버그가 발생할 수 있습니다\.

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-019.png>)

해당 코드는 에러상황에서도 completion을 호출을 해주었지만 또 문제가 있습니다\.

비동기 작업이 중첩되어 작동하기 때문에 콜백이 계속 되는 끔찍한 상황이 발생할 수 있습니다\.

비동기적인 실행을 여러 개 연결해야 할 때, 계속 코드를 들여써야 하는 단점이 발생할 수 있어요\.

![](<../../assets/blog/notion-305facc216d449159c96646e93bc44a7/image-020.png>)

#### 응용

```swift
// 작업을 오랫동안 실행하는 함수
func longtimePrint(name: String) -> String {
    print("프린트 - 1")
    sleep(1)
    print("프린트 - 2")
    sleep(1)
    print("프린트 - 3 이름:\(name)")
    sleep(1)
    print("프린트 - 4")
    sleep(1)
    print("프린트 - 5")
    return "작업 종료"
}
longtimePrint(name: "잡스")


// 비동기함수로 변형
func asyncLongtimePrint(name: String, completion: @escaping (String) -> Void) {
    DispatchQueue.global().async {
        let n = longtimePrint(name: name)
        completion(n)
    }
}
asyncLongtimePrint(name: "잡스") { (result) in
    print(result)
    
    // 메인쓰레드에서 처리해야하는 일이라면,
//    DispatchQueue.main.async {
//        print(result)
//    }
}
```

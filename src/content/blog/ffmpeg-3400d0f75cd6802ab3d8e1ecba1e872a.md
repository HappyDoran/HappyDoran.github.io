모바일 FFmpeg 처리 속도가 기대보다 느리다면 빌드 설정, 영상 규격, 기기 지원 범위, 데이터 이동 경로를 나눠 확인해야 한다\. 라이브러리 파일 교체나 코덱 변경이 어떤 경계를 바꾸는지 중심으로 원인을 정리한다\.

### 1\. 빌드와 플랫폼 가속 연결

Android의 MediaCodec, iOS의 VideoToolbox 같은 플랫폼 가속 경로를 사용하려면 해당 경로가 포함된 빌드인지 확인해야 한다\.

Android 배포 바이너리인 AAR을 바꿨다면 이름·버전만 보지 않고 필요한 가속 지원과 대상 아키텍처가 들어 있는지 확인한다\. 바이너리 교체 사실만으로 기존 병목의 원인이 빌드 옵션이었다고 확정하지 않는다\.

### 2\. 코덱 profile·level

H\.264라는 이름이 같아도 profile·level이 다르면 기기 지원 범위를 벗어날 수 있다\. High·Main·Baseline 같은 profile과 해상도·비트레이트 조건을 함께 확인한다\.

요청한 규격을 하드웨어 경로가 처리하지 못하면 소프트웨어 처리로 돌아갈 수 있다\. 코덱 설정을 낮춰보는 것은 기기의 지원 범위와 입력 조건을 맞추는 점검이다\.

### 3\. SoC별 차이

모바일 SoC마다 영상 처리 블록의 지원 범위와 성능이 다르다\. 특정 해상도·비트레이트에서 가속 경로를 사용하지 못하면 CPU 처리량과 발열이 병목으로 드러날 수 있다\.

성능 차이를 모든 기기에 같은 배수로 일반화하지 않는다\. 입력 영상과 실행 기기, 실제 사용한 처리 경로를 같은 조건으로 비교해야 한다\.

### 4\. WebView와 메모리 복사

하이브리드 앱에서는 Web과 Native 사이의 데이터 복사도 확인한다\. 하드웨어 인코더가 사용하는 Surface 경로와 별개로 프레임을 반복 복사하면 가속 계산을 사용해도 전체 처리 시간은 줄지 않을 수 있다\.

따라서 codec 실행 시간만 보지 않고 프레임 전달·변환·복사 구간을 함께 본다\.

### 정리

가속 실패는 바이너리·입력 규격·기기 지원·데이터 이동 중 어느 경계에서 발생했는지 나눠 조사한다\. 라이브러리나 코덱을 바꾼 결과만으로 원인을 단정하지 않고 같은 조건에서 처리 경로와 병목을 확인해야 한다\.

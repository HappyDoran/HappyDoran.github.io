모바일 이미지 업로드는 촬영 화면을 만드는 것만으로 끝나지 않는다\. 파일 정규화·직접 업로드·분석 제출·결과 조회·정리까지 이어지는 경계를 확인해야 한다\.

아래 목록은 특정 구현의 완료 상태가 아닌, 네이티브와 브라우저를 함께 지원하는 업로드 클라이언트의 점검 기준이다\.

### 캡처와 로컬 이미지

- [ ] captureId와 이미지 메타데이터·최종 바이트의 SHA\-256을 생성하는가
- [ ] 네이티브 임시 파일 registry와 해제 경로가 있는가
- [ ] JPEG 정규화의 최대 크기와 방향·반전 정책을 정했는가
- [ ] N개 keypoint의 ID·고정 순서·좌표 공간을 공통 schema로 검사하는가
- [ ] 카메라·앨범 검출 후 리뷰 조정을 지원하며 미확인 점의 제출을 막는가
- [ ] 브라우저의 사진 선택·검출·조정도 같은 캡처 계약을 만드는가
- [ ] 메모리 이미지의 새로고침 유실을 고려했는가

### 요청·인증 계약

- [ ] builder에서 입력 단위를 전송 단위로 변환하는가
- [ ] 필수·선택 입력값의 범위와 정밀도를 서버 계약과 맞췄는가
- [ ] 파일 형식·크기 상한·checksum·지원 버전을 검증하는가
- [ ] BFF의 HttpOnly cookie 인증과 토큰 갱신 경계를 확인했는가
- [ ] 브라우저에 Bearer token을 노출하지 않는가
- [ ] API 명세와 생성 코드·실제 응답 계약을 대조했는가

### 업로드와 분석 제출

- [ ] 업로드 세션 발급 → 바이너리 PUT → 분석 생성 순서를 지키는가
- [ ] 네이티브·브라우저 PUT이 같은 URL·headers 계약을 사용하는가
- [ ] captureId와 uploadId로 응답을 요청에 연결하는가
- [ ] 사전서명 URL 만료 후 재발급 정책을 정했는가
- [ ] 제출 결과가 불명확한 오류의 중복 방지·복구 계약을 정했는가
- [ ] Idempotency\-Key 지원 여부를 확인했는가
- [ ] 분석 생성 성공·다시 시작 시 로컬 이미지를 해제하는가
- [ ] 실패·취소 후 저장소 객체와 임시 파일의 보존·정리 정책을 정했는가

### 조회와 화면 상태

- [ ] 서버 상태 running·succeeded·failed를 클라이언트 진행 상태와 분리하는가
- [ ] polling 간격·한도·관측 시작 기준을 정했는가
- [ ] 한도 이후 수동 재확인과 내역 조회를 제공하는가
- [ ] SSE·WebSocket·알림의 필요성과 범위를 별도로 판단했는가
- [ ] 조회 재시도와 전체 준비 재시도를 구분하는가
- [ ] 실패 코드·사용 한도 초과를 공통 문구로 안내하는가
- [ ] 화면 전환 lock과 화면 이탈 후 도착한 응답을 처리하는가
- [ ] 대표 지정·선택 삭제·공개 공유의 권한과 캐시 갱신을 확인했는가

### 검증과 데이터 정책

- [ ] builder·schema·경계값·오케스트레이션·query·화면 분기를 자동 검증하는가
- [ ] 대상 환경과 실기기에서 권한·촬영·네이티브 PUT 전체 흐름을 확인하는가
- [ ] 브라우저의 secure context와 저장소 CORS를 확인하는가
- [ ] 이미지·입력값의 접근·보존 기간·삭제·동의 정책을 정했는가
- [ ] 로그에 이미지·민감한 입력값·토큰·서명 URL을 남기지 않는가
- [ ] 테스트 fixture를 실제 provider 연동 성공의 증거로 사용하지 않는가

### 정리

점검 결과는 payload 계약, 파일 수명, 재시도 경계, UI 복구 경로, 운영 정책으로 연결되어야 한다\. 자동 테스트와 실기기 검증을 구분하고, 미결 정책을 구현 완료로 간주하지 않는다\.

### 관련 글

- keypoint 기반 이미지 분석 API 계약
- 네이티브 이미지 업로드와 Web 오케스트레이션
- 이미지 업로드 세션과 비동기 분석 polling 설계
- 사전서명 업로드 URL과 객체 저장소 공개 주소 설계

` props `는 **부모 컴포넌트가 자식 컴포넌트에 전달하는 데이터**입니다\.
` props `는 읽기 전용으로, 자식 컴포넌트는 ` props `를 수정할 수 없습니다\.

```typescript
function ChildComponent(props) {
  props.name = "New Name"; // 오류 발생 가능
  return <div>{props.name}</div>;
}
```

이를 통해 컴포넌트 간의 데이터 흐름을 예측 가능하게 만들고, 컴포넌트의 재사용성을 높입니다\.

` state `는 **컴포넌트 내부에서 관리되는 데이터**입니다\.
` state `는 동적으로 변경될 수 있으며, 컴포넌트의 렌더링에 영향을 미칩니다\. ` state `를 변경하면 컴포넌트는 다시 렌더링되며, UI가 업데이트됩니다\.
` state `는 주로 사용자 입력이나 네트워크 요청의 응답에 따라 변하는 데이터를 관리할 때 사용됩니다\.

### props가 자식 컴포넌트에서 변하지 않는 이유는 무엇인가요? 🤔

` props `가 자식 컴포넌트에서 변하지 않는 이유는 리액트의 **단방향 데이터 흐름 원칙** 때문입니다\. 리액트는 부모 컴포넌트가 자식 컴포넌트에 데이터를 전달할 때 단방향으로 전달하도록 설계되었습니다\. 이렇게 하면 컴포넌트 간의 데이터 흐름을 예측 가능하고 일관성 있게 만들 수 있어 애플리케이션 상태 관리가 간단해집니다\.

` props `는 **읽기 전용**이기 때문에, 부모 컴포넌트에서 전달된 값이 자식 컴포넌트 내에서 임의로 변경되지 않습니다\. 이로 인해, 특정 상태가 어디서 어떻게 변했는지를 예측할 수 있어 버그 발생 가능성을 줄이고 디버깅을 쉽게 합니다\.

만약 ` props `가 변경될 수 있다면, 자식 컴포넌트는 독립적으로 동작하지 않게 되고, 재사용이 어려워질 수 있습니다\. ` props `가 불변으로 유지됨으로써 컴포넌트는 외부 입력에 의존할 뿐 내부적으로 변경하지 않아 재사용성이 높아지고, 코드의 캡슐화가 강화됩니다\.

### 만약 자식 컴포넌트에서 부모 컴포넌트로부터 받은 props를 변경해야 한다면 어떻게 해야 할까요? 🧐

만약 자식 컴포넌트가 부모로부터 받은 ` props `를 변경해야 한다면, 부모 컴포넌트에서 상태로 해당 데이터를 관리하고, 상태 변경 함수를 자식 컴포넌트로 전달하는 방식으로 구현해야 합니다\. 이렇게 하면 데이터는 여전히 단방향으로 흐르고, 상태는 부모 컴포넌트가 관리하므로 일관성을 유지할 수 있습니다\. 이러한 기법을 **상태 끌어올리기**라고 합니다\.

## 면접 답변

#### 💡 \[버전 1\] 핵심만 찌르는 두괄식 답변 \(추천\)

> **&quot;props는 부모 컴포넌트로부터 전달받은 &\#39;읽기 전용&\#39; 데이터이며, state는 컴포넌트가 자기 내부에서 스스로 생성하고 관리하는 &\#39;동적 변경 가능&\#39; 데이터입니다\.&quot;**

두 개념 모두 리액트에서 화면을 리렌더링하는 트리거 역할을 하지만, 관리 주체와 변경 가능 여부에서 명확한 차이가 있습니다\.

- **props \(불변성\)**: 리액트의 **단방향 데이터 흐름** 원칙에 따라 자식 컴포넌트 내부에서 임의로 수정할 수 없습니다\. 이를 통해 데이터 흐름을 예측 가능하게 만들고 컴포넌트의 독립성과 재사용성을 높입니다\.
- **state \(가변성\)**: 사용자 입력이나 API 응답 등에 따라 동적으로 변하는 상태를 표현하며, 상태 변경 함수\(` setState `\)를 통해서만 안전하게 수정해야 합니다\.
- **상태 변경 필요 시**: 만약 자식에서 상위 데이터를 바꾸어야 한다면, 부모의 상태 변경 함수를 props로 내려받아 호출하는 **&\#39;상태 끌어올리기\(State Lifting\)&\#39;** 패턴을 활용합니다\.

#### 📝 \[버전 2\] 꼬리 질문을 방어하는 상세 답변

> **&quot;props와 state는 리액트 UI의 유기적인 변화를 이끄는 핵심축입니다\. props는 외부 파라미터처럼 컴포넌트의 정체성을 정의하고, state는 내부 변수처럼 컴포넌트의 실시간 상황을 대변합니다\.&quot;**

면접관님께서 질문하신 &\#39;props의 불변성&\#39;과 &\#39;데이터 수정 방식&\#39;의 프론트엔드 아키텍처적 의의를 덧붙여 말씀드리겠습니다\.

- **단방향 흐름과 불변성의 가치**: 리액트가 props를 읽기 전용으로 제한한 이유는 애플리케이션의 **&\#39;예측 가능성\(Predictability\)&\#39;** 때문입니다\. 양방향 바인딩을 지원하는 프레임워크와 달리, 리액트는 상위에서 하위로만 데이터가 흐르기 때문에 버그가 발생했을 때 데이터의 근원지\(Source of Truth\)인 부모 컴포넌트만 추적하면 되므로 디버깅이 압도적으로 쉬워집니다\.
- **캡슐화와 독립성 확보**: 자식 컴포넌트가 넘어온 props를 직접 수정하게 되면 부모와 자식 간의 결합도가 극도로 높아져 컴포넌트의 본질인 &\#39;재사용&\#39;이 불가능해집니다\. 자식은 그저 전달받은 props를 UI로 렌더링하는 역할에만 집중하는 캡슐화가 유지되어야 합니다\.
- **상태 끌어올리기\(State Lifting\) 기법**: 그럼에도 불구하고 자식의 이벤트로 부모의 UI를 변경해야 하는 실무적 상황이 빈번합니다\. 이때는 부모가 뷰를 제어하는 상태와 그 상태를 바꾸는 제어권\(함수\)을 통째로 자식에게 위임합니다\. 결과적으로 자식은 부모의 함수를 &\#39;호출&\#39;할 뿐, 데이터는 여전히 부모에서 자식으로만 흐르는 단방향 원칙을 엄격히 고수하며 데이터 무결성을 유지하게 됩니다\.

## 우리가 아키텍처로 해결하고자 하는 것

우리가 코드를 작성함에 있어서 아키텍처를 적용하는 이유는 스파게티 코드를 방지하기 위해서입니다\. 꼬여있는 코드 구성을 방지하고 이해하기 쉽고 확장하기 쉬운 코드 구조를 원합니다\. 유지 보수를 쉽게 하기 위해서도 있죠\. 그렇기 때문에 우리는 이러한 아키텍처 패턴을 적용합니다\.

- 별도의 관심사에 따른 분류\(비즈니스 로직에서 분리된 뷰\)
- 일반적인 작업은 별도의 유틸리티에 위임
- 디자인 패턴은 프레임워크와의 충돌해서는 안됨

## MVSU

이러한 요구사항을 염두에 두고 MVSU라는 디자인 패턴을 설명해보겠습니다\. 이 패턴은 MVC, DDD, Clean Architecture에 강력한 뿌리를 두고 있지만, SwiftUI에 특히 잘 맞는 고유한 속성이 있습니다\. 이 패턴은 4개의 구성 요소 그룹으로 구성됩니다\.

![](<../../assets/blog/mvsu-10d0d0f75cd6807191d0e82accb8d1f9/image-001.png>)

### Utility\(유틸리티\)

단일 특정 작업이나 관련성이 높은 몇가지 작업을 수행하는 좁게 초점을 맞춘 재사용이 가능한 도구입니다\. 이를 통해서 서비스는 하위 수준의 세부 사항에 대한 걱정 없이 기능을 수행할 수 있습니다\.

일부 앱에서 네트워킹, 알림 표시, 오류 처리 등과 같은 일반적인 작업이 있을 수 있습니다\. MVSU는 이러한 유형의 반복되는 일반적인 작업을 utility를 뒤에 붙여서\(NetworkUtility, SessionUtility, LoggingUtility 등\) 규정합니다\.

단일 책임의 원칙에 따라 이러한 유틸리티는 고도로 집중되어야 합니다\. 즉 한가지 유형의 작업이나 몇 가지 매우 관련된 작업만 수행해야 합니다\. 그렇게 하고나서 서비스 계층에서 유틸리티를 활용하여 상위 수준 기능을 수행해야 합니다\. 이와 같은 작업을 유틸리티로 옮김으로써 코드베이스를 깔끔하게 유지하고 반복되는 코드를 작성하지 않으며 서비스 계층에서 해당 도메인에 고유한 작업만 집중할 수 있도록 해야 합니다\. 여기서 알 수 있는 것은 여러 서비스가 동일한 로직을 수행하는 경우에는 유틸리티로 옮겨야 할 가능성이 높다는 것입니다\.

```swift
class NetworkUtility { 
   func  perform < ResultType : Decodable >( request : Request < ResultType >) async  throws -> ResultType { 
      // ...
    } 
} 

class LogUtility { 
   func  log ( type : LogType , description : String ) { 
      // ...
    } 
} 
class FileUtility { 
   func  save ( data : Data , toFileUrl  fileUrl : URL ) throws { 
      // ...
    } 
   func  retrieveData ( fromFileUrl  fileUrl : URL ) throws -> Data { 
      // ...
    } 
}
```

### Service\(서비스\)

서비스는 비즈니스 로직 계층입니다\. 서비스는 애플리케이션의 특정 도메인과 관련된 상태 비저장 기능 그룹입니다\. 뷰에서 사용하는 API라고 생각하면 될 것 같습니다\.

MVC, MVP, MVVM, VIPER와 같은 많은 패턴은 비즈니스 로직을 뷰별로 분리합니다\. 즉 각각의 뷰에 자체적인 별도 컨트롤러, 뷰모델 등이 있는 겁니다\. MVSU에서는 비즈니스 로직을 뷰별로 분리하는 것이 아닌 도메일 별로 분리합니다\. 즉 앱에서 사용하는 각 유형의 데이터는 자체적인 서비스를 받습니다\. 예를 들어서 도넛 가게의 경우 DonutService, OrderService, UserService 등이 될 수 있습니다\.

도메인별로 비즈니스 로직을 분리하면 다음과 같은 장점이 있습니다\. 

- 더 나은 관심사 분리
   뷰 모델과 같은 중재자는 특정 뷰에 연결되도록 설계되었기 때문에, 결국 연관된 뷰에 대해 상당히 많이 알게 됩니다\. 도메인으로 분리하는 것은 서비스가 도메인에 대해 많이 알지만 뷰에 대해서는 거의 알지 못한다는 것을 의미합니다\. 특정 뷰를 염두에 두고 설계되지 않았기 때문입니다\.

- 논리적인 그룹화
   도넛을 만들고 삭제하기 위한 두개의 뷰가 있는 MVVM 앱에서 도넛의 생성 및 삭제 코드는 이 코드와 매우 관련이 있는데도 불구하고 뷰가 두개기 때문에 두개의 다른 뷰모델로 나타내야 합니다\. MVSU앱에서는 모두 단일 DonutService로 끝나기 때문에 관련 코드를 유지 관리하기가 쉽습니다\.

- 서비스 기능의 공유
   서비스 기능은 여러 뷰에서 사용이 가능하기 때문에 뷰간의 기능을 쉽게 공유할 수 있습니다\.
- 보일러플레이트 감소
   MVSU의 경우 뷰에 따른 설계가 아니고 도메인에 따른 설계이기 때문에 뷰에 따른 보일러플레이트는 없지만 도메인당 보일러플레이트는 있습니다\. 이렇게 하면 뷰를 하위 뷰로 나누는 데 따른 단점이 사라집니다\. 이는 뷰 구성이 SwiftUI가 방대한 뷰 컨트롤러 문제를 해결한 주된 이유이므로 아키텍처에서 이를 장려해야 하므로 매우 중요합니다\.

서비스 계층에서 주의해야할 것은 state는 서비스 계층이 아닌 뷰에 저장이 되어야한다는 것입니다\.

```swift
class OrderService {
    private var networkUtility: NetworkUtility
    private var logUtility: LogUtility

    init(networkUtility: NetworkUtility, logUtility: LogUtility) {
        self.networkUtility = networkUtility
        self.logUtility = logUtility
    }

    func createOrder(items: [ItemModel]) async throws -> OrderModel {
        do {
            let response = try networkUtility.perform(request: .createOrder(items: items))
            return OrderModel(record: response.order)
        } catch {
            logUtility.log(type: .error, description: "주문 오류가 발생했습니다: \(error.localizedDescription)")
            throw RuntimeError("주문을 생성할 수 없습니다")
        }
    }
}

```

### Model\(모델\)

모델은 가장 고유하지 않은 부분으로, 앱의 데이터를 캡슐화한 것에 불과합니다\. 서비스는 모델과 통신하여 기능을 수행합니다\. 

모델에는 데이터 유형과 필요한 지속적인 레이어\(Core Data, SwiftData, Realm 등\)가 포함됩니다\. MVSU에서는 SwiftUI의 기능 셋을 유지하는 것이 중요하기 때문에 SwiftUI의 Property Wrapper를 통해서 모델과 직접 통신할 수 있도록 하용해야 합니다\.

### View\(뷰\)

View는 주로 자체 상태 처리를 담당하며, 유틸리티 영역이 아닌 서비스 레이어를 사용하여 기능을 수행합니다\.

MVSU는 개발자가 뷰 구성을 사용하여 큰 뷰를 작은 뷰로 분할하여 각 뷰를 간결하고 좁게 만들고 방대한 뷰 컨트롤러의 문제도 피하도록 권장합니다\. 앞서 얘기한 Service에서는 State가 없다고 했지만 View에서는 필요한 모든 State를 유지합니다\. 

- 관심사 분리
   애플리케이션의 state는 도메인에 따라 나누는 것이 아니라 뷰에 따라 나눕니다\. 따라서 state를 뷰 내에 유지함으로서 유지관리가 쉬워집니다\.

- 향상된 구성과 단순성
   ViewModel과 같은 중간 계층을 다룰 때 뷰 계층을 따라 데이터를 위아래로 전달하는 것은 혼란스러운 과제가 될 수 있습니다\. 비교를 통해서 @Binding, @Environment를 사용하는 것은 매우 간단하므로 구성성을 장려합니다\. 

 

```swift
struct  OrderView : View { 
    @Injected (\.orderService) private  var orderService 
    @Injected (\.paymentService) private  var paymentService 

    let availableItems: [ ItemModel ] 
    @State  private  var itemsInCart: [ ItemModel ] 
    @State  private  var orderAwaitingPayment: OrderModel ? 
    @State  private  var error: 오류 ? 
    
    var body: some  View { 
        VStack { 
            ForEach (availableItems) { availableItem in 
                AddItemToCartButton (availableItem) { item in
                     itemsInCart.append(item) 
                } 
            } 

            Divider () 

            // AsyncButton 뷰를 만드는 것을 적극 권장합니다. https://www.swiftbysundell.com/articles/building-an-async-swiftui-button/ 
            AsyncButton ( "주문 생성" ) { 
                do { 
                    orderAwaitingPayment =  await orderService.createOrder(items: itemsInCart) 
                } catch  let orderError { 
                    error = orderError 
                } 
            } 
        } 
        .sheet(item: $orderAwaitingPayment ) { order in 
            PaymentInfoView (order: order) 
            PaymentButton () { 
                await paymentService.createPayment(forOrder: order) 
                orderAwaitingPayment =  nil
             } 
        } 
        .errorAlert(error) 
    } 
}
```

#### 1\. React에서 상태 관리를 위해 useState와 useReducer를 선택하는 기준을 설명해주세요\.

> 💡 단순한 상태 구현을 넘어, 상태의 복잡도에 따라 적절한 도구를 선택할 수 있는지\(엔지니어링 판단력\)와 UI 컴포넌트에서 비즈니스 로직을 분리해낼 수 있는 설계 능력을 갖추고 있는지 평가하기 위함입니다\.

- ` useState `: 토글 버튼, 카운터, 텍스트 입력과 같이 독립적이고 단순한 상태를 관리할 때 적합합니다\.
- ` useReducer `: 폼\(Form\) 데이터처럼 여러 필드가 얽혀 있는 복잡한 상태 객체를 다루거나, 다음 상태가 이전 상태에 크게 의존할 때 사용합니다\.
- **장점**: 상태 업데이트 로직\(Reducer\)을 컴포넌트 외부로 분리할 수 있어, 뷰\(View\) 컴포넌트 내부가 지저분해지는 것을 막습니다\. 또한 ` dispatch `를 통해 어떤 액션\(` action `\)이 일어났는지 명확하게 통신할 수 있습니다\.

```c++
// useReducer 활용 예시
const initialState = { name: '', age: 0 };

function reducer(state, action) {
  switch (action.type) {
    case 'SET_NAME': return { ...state, name: action.payload };
    case 'SET_AGE': return { ...state, age: action.payload };
    default: return state;
  }
}

function UserForm() {
  const [state, dispatch] = useReducer(reducer, initialState);
  
  // 뷰에서는 복잡한 로직 없이 dispatch만 호출하여 깔끔하게 유지
  return (
    <input 
      value={state.name} 
      onChange={(e) => dispatch({ type: 'SET_NAME', payload: e.target.value })} 
    />
  );
}
```

#### 2\. 리액트에서 커스텀 훅을 사용하는 이유와 장점은 무엇인가요?

> 💡 리액트의 훅 생태계와 라이프사이클을 깊이 이해하고 있는지, 그리고 중복되는 코드를 추상화하여\(DRY 원칙\) 재사용 가능한 클린 코드를 작성할 수 있는지 확인하기 위함입니다\.

- **로직 재사용**: 컴포넌트 내부에 섞여 있는 상태\(State\)와 생명주기\(Lifecycle\) 로직을 재사용 가능한 형태로 분리할 수 있습니다\. 일반 헬퍼 함수와 달리 ` useState `, ` useEffect ` 등의 훅을 내부에서 호출할 수 있습니다\.
- **관심사 분리**: 뷰\(View\)를 담당하는 컴포넌트에서 데이터 패칭이나 이벤트 리스너 등록과 같은 부수적인 선행 처리 로직을 걷어낼 수 있습니다\.
- **명확한 역할**: 결과적으로 컴포넌트는 &\#39;데이터를 받아 렌더링하는 본질적인 역할&\#39;에만 집중할 수 있게 되어 코드가 훨씬 명확해집니다\.

#### 3\. 리액트의 렌더링 성능을 최적화하기 위해 React\.memo, useMemo, useCallback을 어떻게 활용하나요? 

> 💡 리액트 렌더링의 동작 원리를 이해하고 있는지, 그리고 무작정 메모이제이션을 남발하는 것이 아니라 각 도구의 용도와 메모리 트레이드오프\(비용\)를 고려하여 적절히 렌더링 최적화를 할 수 있는지 묻는 질문입니다\.

이 세 가지는 모두 불필요한 연산이나 렌더링을 방지하는 **메모이제이션\(Memoization\)** 도구입니다\.

- ` React.memo `: **컴포넌트 자체**를 캐싱합니다\. 부모 컴포넌트가 리렌더링 되더라도, ` props `가 변경되지 않았다면 해당 컴포넌트의 리렌더링\(비교 연산 포함\)을 건너뜁니다\. 단, 남용하면 메모리 최적화 비용이 더 들 수 있으므로 무거운 컴포넌트에 주의해서 사용해야 합니다\.
- ` useMemo `: 복잡하고 무거운 **연산의 결과값**을 캐싱합니다\. 렌더링될 때마다 동일한 연산을 반복하는 낭비를 막아주며, 동일한 조건에서는 내부적으로 캐싱된 값을 반환합니다\.
- ` useCallback `: **함수 자체**를 캐싱합니다\. 부모 컴포넌트에서 정의된 함수를 자식에게 ` props `로 넘길 때, 부모가 렌더링되면서 함수의 참조값이 매번 바뀌어 자식까지 리렌더링되는 현상을 막아줍니다\.

#### 4\. 리액트에서 useEffect를 사용할 때 모범 사례와 주의할 점을 설명해주세요\.

> 💡 컴포넌트의 생명주기\(Mount, Update, Unmount\)에 따른 부수 효과\(Side Effect\) 처리를 안전하게 할 수 있는지, 특히 메모리 누수 방지\(클린업\)와 의존성 배열에 대한 정확한 이해도를 확인하려는 목적입니다\.

- **비동기 처리**: ` useEffect `의 콜백 함수 자체를 ` async `로 만들 수 없으므로, 내부에서 비동기 함수를 선언하고 호출하는 방식을 써야 합니다\. 이때 반드시 ` try-catch `로 에러 처리를 진행합니다\.
- **클린업\(Cleanup\) 함수**: 이벤트 리스너를 등록하거나 타이머를 설정했다면, 메모리 누수를 막기 위해 ` return ` 문을 통해 클린업 함수를 제공하여 언마운트 시점에 이벤트를 해제해야 합니다\.
- **의존성 배열**: 의존성 배열\(` [] `\)을 어떻게 설정하느냐에 따라 이펙트의 실행 타이밍이 결정되므로, 빈 배열\(마운트 시 1회 실행\)인지 특정 상태를 구독하는지 명확히 해야 합니다\.

```javascript
useEffect(() => {
  const fetchData = async () => {
    try {
      const response = await api.get('/data');
    } catch (error) {
      console.error("데이터 로딩 실패:", error);
    }
  };
  fetchData();

  const handleScroll = () => { /* 스크롤 로직 */ };
  window.addEventListener('scroll', handleScroll);

  // 클린업 함수 (언마운트 시 실행)
  return () => {
    window.removeEventListener('scroll', handleScroll);
  };
}, []); // 빈 배열: 마운트 시 1회만 실행
```

#### 5\. 리액트에서 코드 스플리팅을 구현할 때 React\.lazy와 Suspense를 어떻게 사용하나요?

> 💡 웹 성능 최적화, 특히 초기 로딩 속도\(Bundle Size 최적화\)에 대한 고민을 해보았는지와 비동기 UI 처리 시의 사용자 경험\(UX\) 개선 방법을 알고 있는지 평가합니다\.

앱의 규모가 커지면 초기 번들 용량이 커져 로딩이 느려집니다\. 이를 해결하기 위해 초기 로딩 속도를 줄이는 기법입니다\.

- ` React.lazy `** \(지연 로딩\)**: 초기 렌더링에 당장 필요 없는 컴포넌트\(예: 숨겨진 메뉴, 모달 등\)를 분리하여, 사용자가 버튼을 누르는 등 **필요해지는 시점에 동적으로 청크 파일을 다운로드**합니다\.
- ` Suspense `** \(로딩 UI 처리\)**: 동적으로 파일을 가져오는 동안 사용자에게 빈 화면이 아닌 로딩 인디케이터나 스켈레톤 UI를 쉽게 보여줄 수 있도록 감싸주는 역할을 합니다\.

```javascript
import React, { Suspense } from 'react';

// 동적으로 컴포넌트를 불러옴
const HeavyModal = React.lazy(() => import('./HeavyModal'));

function App() {
  return (
    <div>
      {/* 로딩 중일 때 fallback UI 표시 */}
      <Suspense fallback={<div>Loading Modal...</div>}>
        <HeavyModal />
      </Suspense>
    </div>
  );
}
```

#### 6\. 리액트에서 useContext를 사용해서 상태를 공유할 때의 장점과 주의 사항을 설명해주세요\.

> 💡 리액트의 내장 상태 관리 도구의 한계점을 명확히 인지하고 있는지, 그리고 이로 인해 발생할 수 있는 불필요한 렌더링 폭탄 이슈를 방어할 아키텍처 설계 능력이 있는지 확인합니다\.

- **장점**: 컴포넌트 트리가 깊어질 때, 상태를 계속해서 넘겨주는 **Props Drilling을 방지**합니다\. 중간 컴포넌트들을 거치지 않고 하위 컴포넌트로 직접 데이터를 전달할 수 있어 코드가 간결해집니다\.
- **주의사항**: Provider의 ` value `로 전달된 상태가 하나라도 변경되면, 해당 Context를 구독\(` useContext `\)하고 있는 **모든 하위 컴포넌트가 무조건 리렌더링**됩니다\.
- **해결책**: 하나의 Provider에 여러 상태를 몰아넣는 것은 성능에 좋지 않으므로, 상태 성격별로 Provider를 분리하거나 전역 상태 관리 라이브러리를 적절히 혼용해야 합니다\.

#### 7\. 복잡한 상황에서 컴포넌트 설계 원칙과 전략을 설명해 주세요\.

> 💡 프론트엔드 아키텍처와 디자인 패턴에 대한 주관이 있는지 묻는 질문입니다\. &\#39;단일 책임 원칙\(SRP\)&\#39; 같은 소프트웨어 공학의 기본 원칙을 UI 컴포넌트 설계에 어떻게 녹여내는지 확인합니다\.

컴포넌트는 철저하게 **단일 책임 원칙**에 따라 순수하게 렌더링에 집중하도록 설계해야 합니다\.

- **로직 분리**: 비즈니스 로직은 Custom Hook으로, 복잡한 상태 업데이트는 ` useReducer `나 외부 Store로 분리하여 뷰\(View\)에 대한 처리를 걸러냅니다\.
- **UI 재사용성**: 디자인 패턴을 활용하여 재사용 가능한 UI 로직을 분리합니다\. CSS 측면에서는 Variant\(예: ` primary `, ` size ` 등\)를 사용하여 공통점을 크게 가져가는 구조를 짭니다\.

#### 8\. 리액트에서 성능 문제를 분석할 때 사용하는 도구나 기법에 대해 설명해주세요\.

> 💡 이론적인 성능 최적화 지식을 넘어, 실무에서 마주치는 병목 현상을 실제로 진단하고 디버깅해 본 경험이 있는지\(Troubleshooting 역량\)를 검증합니다\.

- **React Profiler \(개발자 도구\)**: 특정 동작을 녹화하여 컴포넌트의 렌더링 횟수와 렌더링에 걸린 시간을 시각적으로 진단합니다\. 이를 통해 불필요한 리렌더링을 찾아내 최적화합니다\.
- **Chrome DevTools \(Source 탭\)**: SourceMap을 이용해 번들링 되기 전의 원본 소스를 띄워두고, Breakpoint를 걸어 스코프\(Scope\)를 확인합니다\. Call Stack을 왔다 갔다 하며 논리적인 흐름을 디버깅합니다\.

#### 9\. To\-do list를 관리하는 애플리케이션에서 실시간으로 항목을 추가, 삭제, 변경하는 기능을 구현하려고 합니다\. 본인의 경험을 바탕으로, 상태 관리를 어떻게 설계할지 설명해 주세요\.

> 💡 서버 상태와 클라이언트 상태를 구분하는 현대적인 프론트엔드 상태 관리 패러다임을 이해하고 있는지, 그리고 &\#39;낙관적 업데이트&\#39;처럼 사용자 경험\(UX\)을 극대화하는 실무 기술을 알고 있는지 평가하는 종합적인 설계 질문입니다\.

상태를 **서버 상태\(Server State\)**와 **클라이언트 상태\(Client State\)**로 나누어 관리하는 투 트랙 전략이 필요합니다\.

- **서버 상태 관리**: DB와 동기화되어야 하므로 Next\.js의 SSR을 활용하거나, React Query를 사용해 캐싱 및 Invalidate\(무효화\) 로직으로 전체 상태를 자동 업데이트합니다\.
- **클라이언트 상태 관리**: 정렬이나 UI 상태 등은 클라이언트 단에서 관리합니다\.
- **낙관적 업데이트 \(Optimistic Update\)**: 항목 추가/삭제/변경 시, 서버의 응답을 기다리지 않고 **클라이언트 UI에 먼저 즉각 반영**하여 사용자에게 지연 없는 실시간 경험을 제공합니다\. 이후 백그라운드에서 서버와 동기화를 진행합니다\.

#### 10\. 리액트 Virtual DOM이 성능 최적화에 어떻게 기여하는지 설명해 주세요\. 

> 💡 리액트라는 프레임워크를 사용하는 근본적인 이유를 묻는 단골 질문입니다\. 리액트가 화면을 그리는 내부 메커니즘\(Reconciliation, Diffing 알고리즘\)에 대한 탄탄한 기초 지식을 검증합니다\.

브라우저의 실제 DOM을 직접 조작하는 것은 화면을 다시 그리는 과정\(Reflow, Repaint\)을 동반하여 비용이 매우 큽니다\.

- **동작 원리**: 리액트는 메모리 상에 가상의 DOM\(Virtual DOM\) 트리를 만들어둡니다\. 상태가 변경되면 새로운 Virtual DOM 트리를 만들고, 이전 트리와 비교\(Diffing\)하여 **정확히 어떤 부분이 변경되었는지 계산**합니다\.
- **최적화 기여**: 계산된 최소한의 변경 사항들만 모아서 단 한 번 실제 DOM에 일괄 반영\(Batching\)하므로, 불필요한 브라우저 렌더링 연산을 획기적으로 줄여줍니다\.
